# Agent.md

官方默认自动入口是 `AGENTS.md`；本文件保留为更详细的人工参考。若两者冲突，以 `AGENTS.md` 和更安全、更保守的规则为准。

本文件是给在这个项目里工作的 AI Agent / 协作者看的简明约定。目标很简单：说人话、改小步、别乱动文件。

## 项目理解

- 这是 `良禽佳木` 的跨工具 DESIGN 标准包，不只是某一个 OpenClaw skill。
- 日常理解品牌和视觉方向，优先读 `DESIGN.md`。
- 理解项目结构、导出方式和消费层级，优先读 `README.md`。
- 高保真交付、跨工具接入或回归验收时，再按需读 `AGENT-PREFLIGHT.zh-CN.md`、`CONSUMER-GUIDE.zh-CN.md`、`DESIGN-GOVERNANCE.md` 和 `EXECUTION-CHECKLIST.md`。
- `foundation-dna/` 是品牌真源层；`design-packs/` 是受控变化层；`artifact-surfaces/` 是具体交付物约束层；OpenClaw 相关目录只是适配和分发层。
- 品牌名统一写 `良禽佳木`，简称 `良禽`。不要写成 `梁琴` 或 `梁琴佳木`。
- 如果用户明确要求外部风格，如“喜茶风格”，按当前任务方向使用，不要把它写回良禽品牌真源层。
- 涉及 OpenClaw/Hermes/多机器人消费时，按 `/Users/admin/Nutstore Files/我的坚果云/CODE/docs/agent-playbooks/openclaw-hermes-integration.md` 做真实消费面验证。

## 回答方式

- 默认用中文回答。
- 每次解释都要用我能听懂的话说清楚，不要只堆技术术语。
- 如果必须用技术词，先用一句通俗话解释它是什么意思。
- 说明改动时，优先讲三件事：改了什么、为什么改、怎么验证。
- 不要把 CLI 输出、JSON、日志或测试结果直接丢给人看；要先翻译成业务上能理解的结论。
- 如果产物需要人工判断、比较或审批，优先做 HTML / 卡片式 review board，而不是只给原始 Markdown、CSV、JSON 或命令行结果。

## 文件安全

- 不要乱删文件。
- 不要为了“整理干净”删除、移动、重命名现有文件，除非用户明确要求。
- 如确实需要删除或移动文件，必须先说明文件路径、原因、影响范围和可恢复方案，再等用户确认。
- 不要运行 `git reset --hard`、`git checkout --` 等会丢改动的命令，除非用户明确要求。
- 不要覆盖用户已经做过的改动。发现工作区有不相关改动时，保持原样。
- 不要把 `.env`、密钥、token、私钥或凭据内容写进代码、文档或回复里。
- 修改文件前先确认相关文件，不要凭空猜路径、API 或配置。

## 工作方式

- 先看项目现状，再动手。
- 做非简单任务前，先说清楚假设、成功标准和最快验证方式。
- 优先做小而可 review 的改动，不做大范围重构。
- 每一处改动都要能对应到用户当前需求，不做顺手扩展。
- 保持项目现有语言、命名、结构和视觉风格。
- 如果需求有歧义，要把关键假设说出来；风险较大的选择要先停下来确认。
- 对视觉或 UI 问题，不能只靠本地猜测；要尽量验证真实页面、真实尺寸和真实可见效果。

## 这个项目的视觉底线

- 良禽佳木的气质是温润、克制、专业、高级、松弛。
- 高级感来自材质、比例、留白、秩序和中文可读性，不来自夸张特效或促销色块。
- 不要把页面做成电商促销风、冷感国际模板风、炫技动效风。
- 不要编造产品事实、参数、报价、图片来源或案例信息。
- 如果素材、logo、图片或事实不足，要明确写成草稿、占位或待确认，不要假装已经最终可用。

## 验证和交付

- 改代码后，运行最快、最相关的检查。
- 改文档时，至少检查文件是否存在、内容是否完整、是否符合项目命名和语气。
- 最终回复要简洁说明：改了什么、文件在哪里、验证了什么、还有没有不确定点。
