# 良禽佳木单一 DESIGN.md 主控方案设计稿

## 背景

当前仓库已经具备 `foundation-dna/`、`DESIGN.md`、`artifact-surfaces/` 和 OpenClaw skill 协议层，但控制关系仍然偏“多入口”。

实际效果是：

- 品牌宏观气质可以大致传递
- 一旦进入不同品类、不同载体或不同生成链路，模型就容易把局部细节重新发明
- 图标、信息密度、语言风格、系统说明文泄漏等问题，会优先失控

这和当前目标不一致。当前目标不是“给不同渠道定义不同风格”，也不是“让品牌适配所有可能风格”，而是：

**让所有输出，无论品类、渠道、载体，都先服从同一份 `DESIGN.md`。**

## 已确认方向

- 主控制面：`DESIGN.md`
- 控制目标：统一品牌气质、统一语言、统一图标和组件原则
- 适配策略：渠道与品类只影响信息取舍和承载方式，不影响品牌本身
- 设计原则：不追求“全风格兼容”，只追求“同一品牌宪法下的受限表达”

## 核心判断

### 1. 不应把渠道当成风格开关

渠道差异真实存在，但大部分渠道差异本质上是：

- 信息密度不同
- 可展示层级不同
- 交互能力不同
- 图像尺寸和阅读时长不同

这些属于“表达能力约束”，不属于“品牌审美方向变化”。

因此，钉钉、H5、网页、报价长图之间可以有布局差异和信息压缩，但不应各自拥有独立品牌风格。

### 2. 不应把品类当成品牌控制面

品类只应改变内容事实，例如：

- 产品参数
- 工艺说明
- 应用场景
- 咨询承接重点

品类不应决定：

- 语气
- 视觉秩序
- CTA 性格
- 图标语言
- 中文表达方式

否则模型会从“做同一品牌的不同内容”滑向“每个品类重新发明一套表达方式”。

### 3. 品牌需要从“风格描述”升级成“品牌宪法”

当前 `DESIGN.md` 已经包含颜色、字体、布局、组件和禁止项，但在实际生成链路里仍然更像一份“设计说明”，而不是“强制约束”。

下一步应该把它升级成品牌宪法，明确区分：

- 什么是永远不变的硬规则
- 什么是允许变化的表达策略
- 什么是必须被生成器在出图前后自检的门禁项

## 新的控制结构

### 1. `DESIGN.md` = 品牌宪法

`DESIGN.md` 应成为唯一默认入口，且内容分成两层：

#### A. 不可协商层

这部分是所有输出必须继承的内容：

- 品牌气质：温润、克制、可信、安静、耐看
- 中文优先：导航、按钮、标签、说明优先服务中文可读性
- 视觉秩序：摄影、材质、留白、结构优先于装饰
- CTA 语气：邀请式、礼貌、稳妥，避免命令式或逼单感
- 组件原则：按钮、导航、表单、卡片为内容服务，不喧宾夺主
- 图标原则：细线性、几何感、端点克制；弱能力载体允许降级为少图标或无图标
- 禁止项：促销感、电商卡宫格、欧美极简冷感、炫技特效、说明文泄漏到成品

#### B. 允许变化层

这部分只定义变化范围，不定义独立风格：

- 信息密度可高可低
- 首屏可偏编辑式或偏居中
- 区块可长可短
- CTA 出现位置可前可后
- 卡片和图文比例可调整

但所有变化都必须建立在不可协商层之内。

### 2. `DESIGN-GOVERNANCE.md` = 读取与冲突协议

`DESIGN-GOVERNANCE.md` 应进一步收窄职责，只做三件事：

- 定义读取顺序
- 定义冲突处理
- 定义哪些文件只能补充、不能改写品牌

建议明确写成：

- `foundation-dna/` 是真源
- `DESIGN.md` 是默认控制面
- `artifact-surfaces/` 只能描述承载方式
- `design-packs/` 只能做受控表达偏移，不能重写品牌
- `examples/` 只能用来验收，不参与控制

### 3. `EXECUTION-CHECKLIST.md` = 生成器执行清单

新增一份专门给模型读的执行清单，作用不是补充美术描述，而是把抽象规则翻译成可判断的问题。

建议包含三类检查：

#### 生成前检查

- 是否已读取 `DESIGN.md`
- 是否明确识别这次任务的页面目标
- 是否存在把渠道误当成风格切换的倾向
- 是否缺少产品事实但却试图补全“漂亮内容”

#### 生成中检查

- 当前输出是否仍然像良禽佳木，而不是泛高端家居品牌
- 是否出现英文标签、系统说明词、控制面术语
- 是否过度依赖装饰、图标或卡片
- CTA 是否仍然礼貌、稳定

#### 生成后检查

- 是否像成品，而不是规范说明卡
- 是否存在 `Page Goal`、`Pack`、`Design Preview` 之类的元信息泄漏
- 图标是否精细、统一，若做不到是否应直接降级为无图标
- 如果去掉图片，仅看文字和结构，是否仍然成立

### 4. `SKILL.md` = 强制执行器

OpenClaw skill 不再只是“读若干资产后生成”，而应强制执行以下流程：

1. 先读取 `DESIGN.md`
2. 提取品牌硬规则
3. 判断本次任务是“内容变化”还是“承载变化”
4. 在不切换品牌的前提下生成
5. 用 `EXECUTION-CHECKLIST.md` 自检
6. 未通过则重试或降级，而不是自由发挥

### 5. `manual-rubric` = 人工门禁

人工验收必须增加现在缺失的工艺项：

- 是否像真实成品，而不是系统说明图
- 是否存在元信息泄漏
- 图标是否统一、克制、精细
- 是否保住中文界面的完整表达
- 是否因为某个渠道而丢失品牌核心气质

## 渠道与品类的处理原则

### 品类处理

品类只改变内容，不改变品牌。

允许变化：

- 产品事实
- 场景重点
- 功能模块取舍
- 咨询承接方式

不允许变化：

- 语言气质
- 视觉核心
- 图标系统
- CTA 人格

### 渠道处理

渠道只改变承载方式，不改变品牌。

允许变化：

- 信息压缩
- 版式收束
- 交互降级
- 图标减少
- 文案缩短

不允许变化：

- 改成另一套风格
- 为适应渠道而引入促销感
- 为了“显眼”破坏克制和可信

## `DESIGN.md` 的推荐重组方式

建议把 `DESIGN.md` 改成下面的顺序：

1. 品牌主张与一句话宪法
2. 不可协商规则
3. 中文优先规则
4. 图标与组件工艺规则
5. 色彩、字体、间距、层级
6. 允许变化范围
7. 生成原则
8. 禁止项
9. 生成器自检提示

这样模型会先看到“不能变什么”，再看到“可以怎么变”，而不是先读大量视觉描述后自己理解优先级。

## 成功标准

改造完成后，应达到以下标准：

1. 不同品类输出看起来像同一品牌，而不是同类品牌
2. 不同渠道输出看起来像同一品牌的不同承载，不是不同风格模板
3. 图标、文案、CTA、信息层级不再因渠道变化而自由漂移
4. 生成结果更像成品，不像规范说明页
5. 任何新增渠道都不需要先定义一套“新风格”，只需要定义承载边界

## 分阶段落地建议

### Phase 1：收口主控制面

- 重写 `DESIGN.md` 结构
- 把图标规则和中文优先规则前置
- 把“渠道不是风格开关”写成明确原则

### Phase 2：补执行清单

- 新增 `EXECUTION-CHECKLIST.md`
- 把容易失真的问题写成显式检查项

### Phase 3：改 Skill 流程

- 强制先读 `DESIGN.md`
- 生成后执行 checklist 自检
- 不允许缺省状态下自由切风格

### Phase 4：改人工验收

- 更新 `manual-rubric`
- 补充“成品感 / 图标工艺 / 元信息泄漏 / 中文一致性”检查

## 最终建议

这次升级不应该理解成“让品牌兼容所有风格”，而应该理解成：

**把良禽佳木从一套会被不同上下文稀释的设计说明，升级成一套任何输出都必须先遵守的品牌宪法。**

如果这个目标成立，那么未来的品类和渠道扩展都只是在同一宪法下做压缩、取舍和降级，而不是重新定义良禽佳木是什么。
